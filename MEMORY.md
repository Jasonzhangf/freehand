- 2026-07-08: Multi-task foundation design direction is now split into Task Center plus Agent Lifecycle before attaching capabilities to master/worker agents. Task Center owns global task truth: BigTask, SubTask, Execution, Review, EventInbox, SchedulerTick, agent task indexes, registration, synchronization, query, and restart recovery. Agent Lifecycle owns every agent's live runtime semantics: state, current/last activity, elapsed time, model/tool/error counters, error profile, runtime control channel, and AgentBoard. Framework owns timers, scheduler ticks, timeout/stale/blocker detection, event cursors, and projections; Master owns decisions from TaskBoard/AgentBoard; Worker owns execution progress/block/submission/retry updates. Phase 1 scope is one active BigTask with multiple SubTasks and explicitly excludes multiple independent BigTasks and cross-session context switching.

- 2026-07-08: Phase 1 multi-task tool/action surface must stay small and owner-scoped. Semantic action categories can be many in prompts/docs/tests, but exposed tools should be few logical surfaces with typed `op` parameters. Tool name defines owner surface, `op` defines operation, typed args define payload. Unknown op, invalid args, forbidden transition, or permission mismatch must return a paired tool/action validation result to the model, not fallback, not guessed normalization, and not provider/system failure.

# 2026-07-04 agent-framework control principle

- Freehand framework control must be passive and schema/tool-driven: framework defines status fields, prompt guidance, hard status tags, validation/retry policy, built-in action tools, and state executors; the model returns explicit status schema and calls explicit tools; runtime starts/stops/switches tasks only from accepted status/action truth, not from guessed user-request semantics.
- Cross-workspace task/subagent routing should therefore use a no-side-effect invisible status block such as `<<<freehand_status>>>...<<<\/freehand_status>>>` plus a compact built-in `task` action tool for mutation. Public UI strips status blocks, and schema repair/retry handles incomplete or malformed status feedback. Compatibility normalization may repair format shape but must not invent missing task intent.
- Task/subagent control must be centralized metadata/control truth, not data payload forwarding. Parsed status signals and task tool actions write first through `metadata.core` / control center with watermark provenance: writer owner, pipeline node, schema version, status/action, source model/agent/session/turn, timestamp, validation/retry/error trace. Runtime/task/node transitions consume this control-center truth and keep user/request/task data chains separate.
- The next Freehand refactor requires explicit planned owners `control.center`, `error.center`, and `task.orchestration`. Control center handles passive status admission and action-tool admission; error center owns classification/retry/repair/stop/fail/block/cancel decisions; both must write metadata-watermarked records before runtime/reason/task/node state transitions. Design truth: `docs/design/control-error-center-refactor.md`.
- Corrected control model: model feedback has two channels. Status schema is no-side-effect interaction state for reasoning rhythm (`simple_request`, `task_complete`+`evidence`, `next_step`, `blocked`, `needs_user_involvement`+`options`, learned/needs_record). Side effects must use compact built-in action tools, preferably one `task` tool with operation arguments and no more than three framework tools total. Status schema must never execute task mutations.
- Refactor starts with four fixed hook points, not a full-flow hook chain: after local tool result for precise request/tool-result checks; before model request for outbound control; after model response for raw response parsing; before client return for final projection/client-facing processing. Schema variants and action processors may evolve only inside these hook points, not by bypassing them.
